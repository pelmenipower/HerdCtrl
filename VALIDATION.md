## Desktop acceptance procedure

On Ubuntu X11 with `wmctrl`, `xrandr`, and two connected displays:

1. Draw, drag and resize zones on both displays, including one with a negative virtual offset; save, restart and check preservation.
2. Launch `xterm` into each zone and inspect geometry with `wmctrl -lG`. Check resizing after a resolution change.
3. Assign a free global hotkey, save, focus another app, then trigger the view. Confirm conflicting shortcuts are reported.
4. Launch a command that creates no window and verify a timeout message while the editor remains responsive.
5. Disconnect a target display and confirm an error without moving an unrelated window.
6. Check malformed JSON, interrupted saves, and unsaved-close behavior.
7. Measure warm startup to first visible frame and active RSS; record desktop, GPU, monitor scales, executable size and measurements before claiming PRD performance acceptance.

## Existing windows and terminal programs — 2026-11-07

This instruction takes precedence over PRD 4.5's unconditional spawn-first sequence. `PRD.md` was not rewritten. Affected requirements: 4.2 terminal configuration, 4.3 persisted modes, 4.5 reuse/launch pipeline, 4.6 compositor placement and unrelated-window protection.
- Launch workers now reserve an existing eligible window before spawning. Identification uses the dedicated native executable, or a desktop-entry origin for shared launchers/wrappers. A different native executable cannot match merely because it inherited the same desktop marker. Shared interpreters alone and window titles are never sufficient. If several app windows match, the lowest stable available window ID is selected. Reservations prevent one window serving two zones, and complete view runs are serialized outside the UI thread so rapid repeat activation does not race into duplicate launches.
- New windows may also be matched to an identifiable existing application process when a single-instance app delegates window creation. Existing and new placements use PID checks in the GNOME backend; X11 placement now rechecks the current window ID/PID before wmctrl movement. Wrapper/sandbox identity and multi-zone single-instance shortages still have limits documented in README; there is no unconditional matching claim for every desktop app.
- Terminal applications expose Program in terminal as a normal zone property. Selecting a terminal for a legacy custom command preserves that command as the terminal program. Advanced custom commands can use Run in terminal and the configured default terminal. Terminal programs get a real PTY via the terminal executable, rather than the launcher's null stdin/stdout. The command and mode persist with backward-compatible defaults. Dedicated sessions carry their program identity for reuse. An existing external simple command can be matched through descendants only if the terminal PID owns one eligible window; ambiguous shared multi-window terminals are not guessed.
- Added regression checks for executable identity, inherited desktop markers, interpreter ambiguity, distinct window reservations, terminal-program identity, ambiguous terminal windows and terminal-command persistence. The existing new-window exclusion test now exercises the production predicate. The opt-in `gnome_live_terminal_program_has_tty_and_reuses_its_window` test checks that stdin/stdout are TTYs, that the program executes once, and that two rapid repeats reuse the same dedicated window.
